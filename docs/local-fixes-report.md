# open-appsec 修正結果（local-fixes 分支）

本文件說明 `local-fixes` 分支修了什麼、怎麼驗證，以及還有哪些限制。

- 基準：上游 `openappsec/openappsec` 的 `634f840`。
- 分支內容：47 個提交，修改 124 個檔案。
- 最後更新：2026-11-17。

## 驗證方法

每一項修正都經過下列步驟：

1. 在 Ubuntu 26.04（Boost 1.90）上編譯並執行單元測試。
2. 做「還原後失敗」檢查：先移除修正，新測試必須失敗；再放回修正，測試必須通過。
3. 每個提交都經過獨立程式碼審查。審查找到的問題，另外用新的提交修正。
4. 大部分修正也部署到測試環境實測。測試環境是 Kong 加上 open-appsec agent，用 Alpine 重新建置二進位檔。

有些修正加了新的 API 或新的測試目標。這類修正還原後，測試會因為編譯失敗而失敗，不是行為層級的失敗。下表會註明這種情況。

## 效能

測試方法：

- 依序測原版、修正版、修正版、原版。
- 情境有 GET、50 KB POST、XSS。
- 並行數 16、64、256，每組測 2 次，每次 30 秒。
- 每次量測前先暖機 60 秒。

結果：

- **XSS 快約 40%**：政策設定回 403，原版仍送出 274,686 位元組的封鎖頁，修正版回 0 位元組。
- **GET 原本慢約 25%**：原因是提交 27、28、30 讓 IPS 預設檢查 `HTTP_RAW`，提交 28 讓每次關鍵字比對都多做三次查詢。
- **加上提交 46、47 後**：GET 約每秒 3,560 個請求，比只到提交 45 的版本快約 16%；但比拿掉 `HTTP_RAW` 相關提交的版本（約每秒 4,020 個）仍慢約 12%。
- **混合負載**（8 執行緒，GET、20 KB POST、gzip POST）：差異在雜訊範圍內，沒有可辨識的退步。

## 單元測試

- 最新的完整單元測試：53/53 通過。`connection_comp_ut` 會和測試機的 8080 埠衝突，所以沒有列入。
- 提交 45 之前，`rest_server_ut` 在未修改的基準上也會失敗，原因是測試環境的假設。提交 45 修正後，27/27 通過。
- 新增的測試目標包括：`local_policy_mgmt_gen_ut`、`declarative_policy_utils_ut`、`rate_limit_ut`、`waap_parsers_ut`、`manifest_diff_calculator_ut`、`rest_conn_ut`、`nginx_attachment_config_ut`、`shell_cmd_ut`。

## 部署注意事項

- **REST 修正（33）**：程式在 `libngen_core.so`，部署時要換掉這個函式庫。
- **壓縮修正（21–24）**：handler 會連結 `libcompression_utils.so`，要和函式庫一起換。只換 handler 不會生效。
- **IPC 修正（32–35）**：要換 `libshmem_ipc.so`。
- **部署後檢查**：曾發生函式庫沒有換到、攻擊又被放行的情況，所以部署後一定要重跑攻擊測試確認。
- **Redis 命令逾時（16）**：沿用 Redis Timeout 設定，預設 30 毫秒。Redis 回應比這個慢時，限速會放行並重新連線（5 秒冷卻）。部署前請確認這個值。
- **Snort 轉換（18）**：非空的 Snort 檔如果全部規則都轉換失敗，政策產生現在會失敗。原本是無聲略過。

## 限制與沒有驗證的項目

- 提交 21 到 23 還原後的失敗，多數是無法編譯，不是行為層級的失敗。
- 預設 256 MiB 的輸出上限仍可能占用大量暫時記憶體。nginx parser 和 WAAP 的呼叫端還沒有傳入更低的上限。
- 用 300 MB 和 600 MB 的 gzip 炸彈實測時，原版和修正版的記憶體峰值差不多，分不出差異。輸出上限（21）只有單元測試驗證。
- IPv6 限速（16）：測試環境的流量都轉成 IPv4 來源，只有單元測試驗證。
- 含點號的鍵名（23）：實測時原版和修正版結果相同，只有單元測試驗證。
- manifest（26）：測試的部署模式沒有路徑會觸發，只有單元測試驗證。
- 自訂回應（14）：`nginx_attachment` 沒有測試目標，只實測了 XXE。
- 跨 user namespace 的 IPC 權限（35）：只有單元測試和同一個 namespace 的實測，沒有實測真正跨 namespace 的 attachment。
- C07 的 WAAP 部分（`webUserResponsePerPractice` 沒有寫入）沒有直接修正。
- 提交 20 只測到單元層，沒有跑完整的 orchestration 輪詢流程。
- 雲端中控：Snort 規則 9100102（`http_stat_code`）沒有送到雲端政策，原因還沒查明。
- handler 被 `kill -9` 後，watchdog 在 1 秒內重新啟動，但 Kong 會持續放行超過 5 分鐘。原版也有同樣的行為，不是這些修正造成的。
- 有些審查回報「沒有發現」，這不代表保證沒有問題。
